## Recovery/rollback procedure to make concrete

1. **Before promotion:** the observed alias currently resolves to rollback candidate `dpl_HascaVEdQyPsMz6cwCXLn2fV6vwi`. Reconfirm alias, source and availability immediately before promotion, and verify candidate behavior. This read-only discovery is not a rollback drill. Keep the tested new candidate ID separately; never treat a preview URL as the production rollback target.
2. **Before traffic changes:** record which Blob store and database are production, their existing recovery options and access path without secrets. Test recovery into isolated resources using synthetic data. Blob recovery protects submission content; database recovery protects status/history. Rebuilding the index from Blob does not reconstruct status-history events and is not a complete database backup.
3. **Promotion:** deploy/promote only the visually approved candidate with checked production bindings. Note time/source/deployment and run bounded public/private synthetic smoke immediately.
4. **Rollback trigger:** core route failure, lost/private-save failure, unauthorized data access, unusable owner access or false success prevents acceptance. Restore the recorded good application deployment and stop affected acquisition if necessary; retain customer records.
5. **Compatibility:** rollback to the earlier pilot may remove the new owner UI/v2 handler even though newly saved v2 records remain intact. Preserve provider-level private recovery access, do not rewrite those records, and do not claim an older app exposes every new feature. In-flight clients may need refresh; a failed retry must not claim saving. Diagnose before re-promoting.
6. **After rollback:** verify the restored public flow and private retrieval path, reconcile only through authorized operations, and document what remains inaccessible. Never delete Blob records/drop tables or overwrite live data as a code rollback step.

If selected provider recovery features are unavailable without payment, report the actual limitation and concrete alternatives/cost before asking the owner. No unverified backup schedule, retention window, RPO or RTO is promised here.

## Proposed lightweight operating choices — not commitments

These are reasonable defaults for owner consideration, not invented service promises or extra software requirements:

- **Inbox:** owner reviews New requests once each business day and after an incident; replies manually from hello@levarum.com; records Contacted after actually sending, Done when closed, Booked only after an agreed call. No public response-time promise accompanies this proposal.
- **Index coverage:** check reconciliation state during that review; run the existing bounded reconciliation if it is incomplete or a known saved request is missing. Avoid exporting a full customer list for routine troubleshooting.
- **Ownership:** initially the confirmed sole owner handles both lead and privacy requests; no assistant or additional staff is presumed available.
- **Privacy:** review closed requests periodically for continued need, verify the requester before access/deletion, and keep a minimal completion record without copying the deleted content. Do not publish a numeric retention period until the owner selects a real practice and any applicable obligations are understood.
- **Recovery:** keep a private short runbook listing provider entry points, deployment rollback ID, recovery steps and actual selected-plan limitations. Do not put credentials in the runbook or add paid tools before need/cost is established.

The owner can confirm these operating choices together with the final review rather than being asked repeatedly during implementation. Their confirmation is necessary because only they can commit to ongoing review or retention practice; it does not block design, tests, source saving or preview work.
